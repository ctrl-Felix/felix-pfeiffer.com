# Guidelines

- The owner writes no code. All code, docs and text are written by Claude.
- No code documentation or comments. No human reads the code.
- Keep chat replies short. Do not trade code clarity for brevity: no minifying, no cryptic names.
- Keep files small and focused so they are cheap to read.
- Keep all user-facing text short and relevant to the page or tool it appears on. Do not explain other apps there (for example no Whois or Tools notes on the Stats page).
- Branch flow is mandatory. All work happens on the branch `staging`, there is no other branch (Dependabot also targets `staging`). Commit and push to `staging` only. Nothing runs and nothing deploys on a push to `staging`. `main` is protected: it only changes through a pull request from `staging` and all CI checks must pass. Coolify deploys `main`. Open the pull request and merge it only when the owner asks, and only after every check is green. Never push to `main` directly and never bypass the branch protection. Run lint, `npm test` and the build locally before pushing. Security still comes first while writing code, CI is only the last line.
- Handling Dependabot: its branches are merged into `staging` locally (`git merge origin/dependabot/...`), each update is checked with lint, tests and build first, workflow file bumps are applied by hand when the merge conflicts, rejected updates get `@dependabot ignore this major version`. Merging pull requests happens only on the owner's request.
- Keep this file current: stack, structure and conventions go below.

# Project

Personal portfolio of Felix Pfeiffer (MSc Information Security @ UCL, ex Fraunhofer IOSB, BaFin, AXA, co-founder of Cosmoshield and Pakt). Experiment in how far AI can take a real project.

# Mission

1. Rank first on Google for "Felix Pfeiffer".
2. Be easy for AI assistants and AI search to find, read and cite.

SEO and AI optimization come before visual polish when the two conflict. Every change must keep:
- Real, crawlable text in the HTML (no content only inside images or client-only code).
- Correct metadata, canonical URL, JSON-LD `Person`, `sitemap.xml`, `robots.txt`, `llms.txt`.
- Fast loads and good Core Web Vitals.
- Facts consistent with LinkedIn and GitHub (name, role, links).
Site config and facts live in `src/config.ts`.

# Stack and structure

- Next.js (App Router), TypeScript, Tailwind. Next.js 16 differs from training data: read `node_modules/next/dist/docs/` before using its APIs.
- AI features: Vercel AI SDK with Claude (not installed yet).
- Self-hosted with `docker compose` (deployed on Coolify as a Docker Compose application): services `db` (Postgres 17, built from `db/Dockerfile` with the role script baked in), `migrate` (dbmate, built from `db/migrate.Dockerfile` with the migrations baked in, runs `up` before the app starts) and `web` (Next `standalone`). All hardened: dropped caps, read-only, no-new-privileges. `db` and `migrate` are only on the internal `backend` network. `web` only `expose`s 3000: Coolify routes the domain to it. Locally add `docker-compose.local.yml` to publish `127.0.0.1:3000`.
- Configuration is plain environment variables, listed in `.env.example`: `DB_SUPERUSER_PASSWORD`, `DB_MIGRATOR_PASSWORD`, `DB_APP_PASSWORD`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `CONTACT_TO`. On Coolify set them in the app's Environment Variables. Locally `scripts/init-env.sh` writes a `.env` with random database passwords, then `docker compose -f docker-compose.yml -f docker-compose.local.yml up -d --build`. `web` only gets the app password and SMTP values, never the superuser or migrator password. The database roles are created once on first init of the data volume, so changing a password later needs `ALTER ROLE` as well.
- Migrations live in `db/migrations` as dbmate SQL with `-- migrate:up` and `-- migrate:down`. Always write both. Roll back with `docker compose run --rm migrate rollback`, check with `docker compose run --rm migrate status`. Roles are created once by `db/roles.sql` (via `db/init/01-roles.sh`) on first database init: `portfolio_migrator` owns the schema, `portfolio_app` only gets the grants a migration gives it (currently select and insert on `events`, kinds visit, click and mcp).
- Next.js connects to the database in server code only: `src/lib/db.ts` (the only place that imports `pg`), route handlers, and `use cache` queries in `src/lib/stats.ts`.
- Source in `src/app` (pages, `stats`, `api/contact`, `api/track`) and `src/components` (macOS UI: menu bar, dock, desktop icons, window manager in `windows/`, Profile, Mail, SEO Tracker, Tools, Stats, Public Paths and Finder).
- Windows: `windows/WindowManager.tsx` owns state (one window per app id), `windows/Window.tsx` is the frame (drag, resize, minimize, zoom, close). App content uses `useWindow()` for traffic lights and drag handles. Register new apps in `src/components/apps.tsx`.
- SEO Tracker app (`components/seo`, id `seo`, desktop icon, transient in the dock) is a placeholder window that says TBD. The Stocks app was removed; clicks recorded for it earlier still show as Stocks in the stats through `legacyTargets` in `src/lib/tracking.ts`.
- Tools app: `src/components/tools/registry.tsx` lists the tools (searchable in the window); add a tool by adding an entry with its component. DNS Records (`DnsTool.tsx`) uses `lookupDns` from `src/lib/dnsLookup.ts` via `GET /api/tools/dns` (rate limited, 20 per minute per IP, same code as the MCP tool `dns_records`). Whois uses `src/lib/whois.ts` via `GET /api/tools/whois`: RDAP first (endpoints from the IANA bootstrap file, cached 24h), raw WHOIS on port 43 as fallback, no API keys. Parsing lives in `src/lib/rdapParser.ts` (RDAP: registrar with IANA ID and abuse contact, dates, EPP statuses explained in `eppStatus.ts`, name servers with glue addresses, DS records with algorithm names, contacts with redaction flags, notices) and `src/lib/whoisTextParser.ts` (port 43 text for many registry layouts, dates in `whoisDates.ts`); the shape is `WhoisResult` in `src/lib/whoisTypes.ts` and the UI is `WhoisResultView.tsx`. The text parser fixtures in `whoisTextParser.test.ts` are representative samples written from memory, not captured responses. Output that has no registration data at all counts as a failed lookup. Input is strictly validated as a domain, rate limited (12 per minute per IP), results cached 10 minutes, nothing stored. `RDAP_BOOTSTRAP_URL` and `WHOIS_ROOT_SERVER` override the sources for tests.
- TLD coverage: `src/data/tldCoverage.json` maps every IANA TLD to true (an RDAP endpoint in the IANA bootstrap or a public WHOIS server from `whois.iana.org` exists) or false. `npm run tld:update` (`scripts/update-tld-coverage.ts`, logic and tests in `src/lib/tldCoverage.ts`) rebuilds it from the IANA list and keeps the old value when a check errors. The Whois tool shows it behind the `i` button (`TldCoverage.tsx`). The `tld-coverage` CI job runs the update on pull requests (and on the `workflow_dispatch` run described next) and the `tld-coverage-commit` job commits a changed file to `staging` (the only job with write permission, it runs no repository code, only for pull requests from `staging` itself). A commit made with the workflow token does not start CI, so that job then starts CI again on `staging` with `gh workflow run`, so the checks appear on the new head commit; the rerun finds no change and stops. The sandbox cannot reach `data.iana.org`, so the file is only filled by CI or a machine with internet.
- Token tracker: `npm run tokens:update` (`scripts/update-token-usage.ts`) reads all Claude Code transcripts of this project on the machine (including subagents) into the ledger `src/data/tokenUsage.json`: one line per API message, keyed by a hash of the message id, values are the model id and the input, output, cache write and cache read tokens, merged with the per-field maximum (old entries without a model count as unknown until their transcript is read again). That makes it idempotent: reruns, resumed or forked sessions and streamed duplicates never count twice, and old sessions stay in the ledger. A `PreToolUse` hook (`.claude/hooks/update-tokens.sh`) runs it before every `git commit`, so each commit carries the current number. The README text in the Reader shows the total and a list per model, and the hidden `tokens` app (Apple menu, Token Usage…, `components/tokens`) shows totals, requests and the share per model (`src/lib/tokenUsage.ts`). Tokens used after the last commit of a session are lost if the session ends before the next commit.
- Public paths: the hub `/tools` (`src/app/tools/page.tsx`, `ToolsHubSeo`, data in `toolsHub`) lists every tool, and every tool has a crawlable page at `/tools/<id>` (`src/app/tools/[tool]/page.tsx`, params from `src/data/tools.ts`) with metadata, canonical URL, `WebApplication` JSON-LD and real text (`ToolSeo`). It renders the same desktop and auto-opens the tool maximized (`Desktop launch`, `components/deepLink.ts`; `?domain=` prefills Whois). `src/data/publicPaths.ts` is the single list of public addresses, grouped (Site, Tools with the tool pages under the hub, For AI assistants) as the Public Paths window shows them: it feeds the sitemap, `llms.txt` and the Public Paths window (Apple menu → Public Paths…, a hidden app in `apps.tsx`). Adding a tool means adding it to `src/data/tools.ts` and `registry.tsx`; everything else follows.
- MCP: one endpoint, `POST /mcp`, for every tool. Next cannot put a route next to the page `src/app/mcp/page.tsx`, so `src/proxy.ts` rewrites POST, DELETE and event stream GET requests on `/mcp` to the internal handler `src/app/api/mcp/route.ts` (browser GETs get the explanation page). The protocol is hand written and stateless (Streamable HTTP, no auth, `src/lib/mcp.ts`); tools live in `src/lib/mcpTools/` and are registered in `index.ts` (`McpTool`: schemas, annotations and a `call`). Tools today: `whois_lookup` and `dns_records` (`src/lib/dnsLookup.ts`: Node resolver pinned to public resolvers 1.1.1.1, 8.8.8.8 and 9.9.9.9, `DNS_RESOLVERS` overrides them, public names only, 60 second cache). The endpoint validates Origin, limits body size, rate limits per IP and globally per tool, and stores nothing. Add a tool by adding a file in `mcpTools/`, registering it, listing it in `src/data/mcp.ts` and testing it. Listed in `llms.txt` and documented in the Whois tool window. `robots.txt` disallows only `/api/`.
- MCP page: `/mcp` (`src/app/mcp/page.tsx`, `/mcp-servers` redirects to it, content in `src/data/mcp.ts`, indexed, FAQ and TechArticle JSON-LD, OG image) explains MCP and how to connect to the single server. The menu bar has an `MCP` menu on the right (`McpMenu.tsx`) listing the entries of `mcpConnectors` with Copy URL and a link to the page.
- Reader apps: `README.md` and `Security.md` icons (bottom right by default) open the `Reader` and `Security` windows (`components/reader`, both use `DocumentReader`) showing `src/data/readme.ts` and `src/data/security.ts`, rendered by the small safe parser in `src/lib/markdown.ts`. The text is written in the first person as Felix, short, no em dashes. Both are transient in the dock, as are Tools, SEO Tracker and Stats.
- Desktop icons are draggable and snap to a grid (`DesktopIcons.tsx`), default layout in columns on the left, positions saved per browser in localStorage (`desktop.icons`).
- Tool pages are SEO pages: absolute title and description in `src/data/tools.ts`, FAQ and breadcrumb JSON-LD, generated Open Graph image, sitemap `lastmod`, 404 for unknown tool paths via `src/proxy.ts` (otherwise the first request would be a soft 404 with status 200).
- Profile content lives only in `src/data/profile.ts` and feeds the Profile window, the hidden SEO text and JSON-LD. Never put the phone number on the site.
- Mail window posts to `/api/contact` (nodemailer, SMTP settings in `.env`, honeypot and per-IP rate limit).
- Glass look is the `.glass` class in `globals.css`. Keep it inside `@layer components` so Tailwind utilities can override it. Glass is for the functional layer (dock, toolbars, menus). Content cards use plain translucent fills.
- Brand icon: `src/app/icon.svg` (F and P monogram on a blue tile). `favicon.ico` and `apple-icon.png` are rendered from it. Regenerate them if the SVG changes.
- Do not use `pkill -f` in the shell, it kills the tool shell. Use `fuser -k <port>/tcp`.

# Privacy and tracking

- The only tracking is `/api/track`, shown as aggregates on `/stats` and in the Stats window (same `StatsBody`, data from `/api/stats`, no list of single events). It stores time, kind (visit or click), a whitelisted target and a daily anonymous visitor hash. Visits count once per visitor per day and clicks once per visitor, app and day (unique indexes). The hash uses a random per-day salt kept in the `daily_salts` table (old salts are deleted, so it survives redeploys but cannot be linked across days) and only the IPv4 address or IPv6 /64 prefix. `?notrack` on any address sets a local opt-out, `?notrack=off` removes it. No cookies, no IP, no user agent storage. DNT, GPC and bots are ignored.
- MCP usage is tracked too: every `tools/call` of a registered tool is stored as kind `mcp` with the tool name as target and no visitor ID, not deduplicated (`recordMcpCall` in `src/lib/events.ts`, called through `after()` in `src/app/api/mcp/route.ts`; migration `20261012000000_mcp_events`). `/stats` shows calls by tool and calls over time. Tools must be whitelisted in `mcpTargets` in `src/lib/tracking.ts` (a test fails when a registered tool is missing). Anything new that is tracked must be added to the whitelist in `src/lib/tracking.ts`, shown on `/stats` and described in the transparency text there. Never add third-party analytics.

# Security rules

- Security is a key factor of every feature and is always considered, before and after a change. Rights are always minimal: no root, no extra Linux capabilities, read-only filesystems, least-privilege database roles and the narrowest grants, scopes and permissions that work. Never widen rights to make something easier.
- Credentials only come from environment variables (Coolify env or an untracked `.env`) read through `readSecret()` in `src/lib/secrets.ts`, which also supports `NAME_FILE`. Never put a secret in code, `docker-compose.yml`, `.env.example`, URLs, logs, commits or chat. Compose requires them with `${VAR:?}` so a missing one fails fast. Never read or print `.env` (blocked in `.claude/settings.json`).
- SQL only with `$1` placeholders. ESLint blocks interpolated SQL, direct `pg` imports and direct `process.env.*PASSWORD` reads. Do not disable these rules.
- Public endpoints validate input, rate limit with `src/lib/rateLimit.ts` and return no internal details.
- Vulnerability Tracker (app `vulnerabilities`, `components/security/VulnerabilityWindow.tsx`, data via the static route `/api/vulnerabilities` from `src/lib/vulnerabilities.ts`): one JSON file per real vulnerability in `security/vulnerabilities/<id>.json` (id, title, explanation, severity from the CVSS band, CVSS score and vector, scanner, identifier, location, url, detected, status open or fixed, fixed date, pull request). Only real vulnerabilities belong there: a CVSS score is required, and hardening hints, misconfigurations (for example Trivy or hadolint findings such as running as root), secrets, code quality results, dev only dependencies and unfixable base image CVEs are not recorded. The CI job `vulnerability-record` collects the scanner output of the pull request (npm audit JSON from `quality`, CodeQL SARIF from `codeql`, Trivy image JSON from `container`), `scripts/record-vulnerabilities.ts` (parsers in `src/lib/vulnerabilityScan.ts`, tested with fixtures that are not captured real output) adds new findings, marks findings that are gone as fixed and reopens returning ones, and fails the pull request for a CVSS of 7.0 or higher. A scanner without usable output leaves its entries unchanged. The job `commit-generated` (the only job with write permission, runs no repository code, validates every file with jq, only for pull requests from `staging`) commits changed files to `staging`. Never create or edit these files by hand to make numbers look better.
- CI (`.github/workflows/ci.yml`) runs only on pull requests to `main` (plus the `workflow_dispatch` rerun after a TLD commit): lint, unit tests (`npm test`, node test runner with tsx, including `tests/security.test.ts` which checks container hardening, non-root users, network exposure, secret handling, security headers and workflow permissions), build, npm audit, gitleaks, CodeQL, a migration up/down/up test with a least-privilege check, hadolint, Trivy, and the TLD coverage check (non blocking). There is no paid AI review in CI. Dependabot updates npm, Docker, Compose and Actions weekly into `staging` (minor and patch updates grouped; majors of `node` and `@types/node` stay on the Node 22 LTS runtime and `typescript` majors wait for `eslint-config-next` support, so those are ignored). Keep CI green. Run the `security-review` skill before large changes.
